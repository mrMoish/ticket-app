# Заявки на автоматизацию

Небольшой веб-сервис: сотрудник регистрируется, создаёт заявки на автоматизацию (бот, интеграция, отчёт, другое),
возвращается к ним позже, редактирует и сам меняет статус.

**Стек:** FastAPI + Jinja2 (интерфейс без сборки), Supabase Auth (почта + пароль) и Supabase Postgres.

## Запуск

1. **Supabase.** Создайте проект на [supabase.com](https://supabase.com).
2. **Схема.** Dashboard → SQL Editor → вставьте содержимое [`supabase/schema.sql`](supabase/schema.sql) → Run.
   Скрипт создаёт таблицу `tickets`, ограничения, триггер и политики RLS. Его можно запускать повторно.
3. **Ключи.** Project Settings → API: скопируйте `Project URL` и публичный ключ (`anon` или `sb_publishable_…`).
4. **Приложение:**

```bash
cp .env.example .env        # впишите SUPABASE_URL и SUPABASE_ANON_KEY
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Откройте http://127.0.0.1:8000.

## Как устроено ограничение доступа

Приложение **не** фильтрует заявки по пользователю в коде и **не** использует service-role ключ. Все запросы к данным
идут в Supabase с JWT самого пользователя, а доступ ограничивает база (`supabase/schema.sql`):

- включён RLS, политики `select / insert / update` разрешают строки только при `auth.uid() = user_id`;
- `user_id` подставляется базой (`default auth.uid()`), клиент его не передаёт; триггер не даёт сменить владельца,
  `id` и `created_at`;
- вставить можно только заявку со статусом `new`; допустимые категории и статусы закреплены `check`-ограничениями;
- роли `anon` права на таблицу отозваны, удаление заявок не выдано никому.

Поэтому чужие заявки недоступны и при прямых запросах к REST API Supabase. Проверить это можно скриптом:

```bash
python scripts/verify_rls.py
```

Он создаёт двух тестовых пользователей и 11 проверок делает напрямую через PostgREST: чтение, изменение, подмена
владельца, анонимный доступ, удаление. Для скрипта в Supabase должно быть выключено подтверждение почты.

## Что где

| Файл | Назначение |
|---|---|
| `app/main.py` | сборка приложения, middleware сессии (тихое обновление токена) |
| `app/supa.py` | клиент Supabase Auth и PostgREST, перевод ошибок в понятные сообщения |
| `app/routes/auth.py` | регистрация, вход, выход |
| `app/routes/tickets.py` | список, поиск и фильтр, создание, редактирование, смена статуса |
| `app/domain.py` | категории, статусы, валидация |
| `app/templates`, `app/static` | адаптивный интерфейс |
| `supabase/schema.sql` | таблица, RLS, триггер, права |
| `tests/` | 17 тестов логики на имитации Supabase |
| `scripts/verify_rls.py` | проверка RLS на живом проекте |

## Поведение, на которое стоит обратить внимание

- **Дубли.** Форма создания получает уникальный `id` при открытии. Кнопка блокируется после нажатия, а если
  запрос всё же уйдёт дважды (двойной клик, повтор после обрыва), второй упрётся в первичный ключ и
  вернёт ту же заявку, а не создаст новую.
- **Сохранение.** После отправки действует схема POST → redirect → GET: обновление страницы не отправляет форму
  повторно. Результат виден в сообщении («Заявка создана», «Изменения сохранены», «Статус … изменён»).
  При ошибке (нет сети, сбой Supabase, невалидные данные) форма остаётся с введёнными данными и понятным текстом.
- **Сессия.** Токены лежат в `HttpOnly`-cookie с `SameSite=Lax`; истёкший access-токен обновляется автоматически.
  В продакшене на HTTPS задайте `COOKIE_SECURE=true`.
- **Телефон.** Таблица на узком экране превращается в карточки, элементы управления высотой от 44 px.
- **Ограничения.** В списке показываются последние 200 заявок (постраничности нет); поиск ищет по подстроке названия
  без учёта регистра.

## Тесты

```bash
pip install -r requirements-dev.txt
pytest
```

Тесты прогоняют полный сценарий (регистрация, вход и выход, создание, дубли, ошибки, поиск и фильтр, правка,
статусы, изоляция пользователей, обновление токена) на имитации Supabase без сети. Настоящий RLS они не проверяют.
Для этого есть `scripts/verify_rls.py`.
